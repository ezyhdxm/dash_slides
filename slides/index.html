1 · Plotly alone

Plotly: interactive figures, no server

fig.write_html("plotly_only.html")

1 · Plotly alone

Where Plotly alone stops

Fine in the browser
  • zoom, pan, hover, select
  • toggle traces in the legend
  • dropdowns/sliders that switch between data already in the file
Needs Python again
  • "show me Energy only", recomputed
  • query a database, call a model, run a pricer
  • data too big to ship into one HTML file
  • one chart driving another, with real logic
Plotly has no back end. Once the HTML is written, nothing can ask Python a new question.
2:15–3:00. The browser can only rearrange what it was given. Anything that needs computation means re-running the script and re-sending the file.
1 · Why a server

Plotly vs Dash

3:00–5:15. The key picture of the talk. Left: Python's job ends when the file is written. Right: the server stays up. The browser keeps the page and the widget values; when a value that matters changes, it sends a small JSON message; Python answers with new values for parts of the page. Everything else in the talk is details of this loop.
2 · Building a page

The smallest Dash app


from dash import Dash, html, dcc
import plotly.express as px
from data import bonds

app = Dash(__name__)        # Flask server + Dash front end

fig = px.scatter(bonds, x="maturity", y="spread", color="sector")

app.layout = html.Div([     # the page: a tree of components
    html.H1("Corporate bonds"),
    html.P(f"{len(bonds)} bonds"),
    dcc.Graph(figure=fig),  # any Plotly figure goes here
])

if __name__ == "__main__":
    app.run(debug=True)     # http://127.0.0.1:8050
5:15–6:45. Demo 02. Step through the highlighted lines (arrow key). debug=True gives hot reload and the error panel. Note there is no HTML, no JavaScript: the layout is Python objects.
2 · Building a page

A layout is a tree of components

  • html.*: one class per HTML tag: Div, H1, P, Table, Button…
  • dcc.*: interactive pieces: Graph, Dropdown, Slider, Tabs…
  • Each component has props: children, style, className, value, figure…
  • An id names a component so callbacks can read or write its props
  • CSS files in assets/ are loaded automatically
6:45–7:45. The layout is data, not a page: Dash sends it as JSON and the renderer in the browser builds the HTML. That's why every prop must be JSON-serialisable.

3 · Callbacks

A callback: "when this changes, run that"


from dash import Dash, html, dcc, callback, Output, Input

app.layout = html.Div([
    html.H1("Corporate bonds"),
    dcc.Dropdown(sectors, "Banks", id="sector"),
    html.P(id="summary"),
    dcc.Graph(id="chart"),
])

@callback(Output("summary", "children"),
          Output("chart", "figure"),
          Input("sector", "value"))
def update(sector):
    print(f"server: update({sector!r})")
    d = bonds[bonds.sector == sector]
    text = f"{len(d)} {sector} bonds, avg {d.spread.mean():.0f} bp"
    fig = px.scatter(d, x="maturity", y="spread", color="issuer")
    return text, fig
Input = (id, prop) to watch.
Output = (id, prop) to fill with the return value.
10:15–11:45. Demo 04. Pick Energy and show the terminal line "server: update('Energy')": the function runs on the server, not in the browser. Outputs are filled in order from the returned tuple.

The callback toolkit

which input fired?ctx.triggered_id

15:00–16:15. Don't teach each; just show they exist. Two rules worth saying: callbacks should not rely on global state (many users, many workers), and each output prop belongs to one callback.
4 · Click to drill down

Click a bond, see its history


overview = px.scatter(bonds, x="maturity", y="spread",
                      color="rating", hover_name="issuer",
                      custom_data=["cusip"])   # rides along with each point

app.layout = html.Div([
    dcc.Graph(id="overview", figure=overview),
    dcc.Graph(id="detail"),
])

@callback(Output("detail", "figure"),
          Input("overview", "clickData"))
def show_history(click):
    if click is None:                     # page load: nothing clicked
        cusip = bonds.cusip.iloc[0]
    else:
        cusip = click["points"][0]["customdata"][0]
    h = history[history.cusip == cusip]
    return px.line(h, x="date", y="spread", title=cusip)
16:15–17:45. Demo 05. The trick is custom_data: attach the key you need (cusip) to every point; the click sends it back. Using x/y to find the bond would be fragile.

A click is just another prop change. Same loop as the dropdown: any chart can drive any other.
17:45–20:15. The point: there is no special drill-down machinery. A click sets a prop in the browser; because that prop is an Input, the usual POST happens. customdata is the cusip we attached. Also works with hoverData (hover to preview) and selectedData (lasso a group).

5 · VS Code + Copilot

Give Copilot the rules once

demos/.github/copilot-instructions.md is read with every request in this workspace:


- Use Dash 3 or later. Import with
  `from dash import Dash, html, dcc, callback, Output, Input`.
  Do NOT use dash_core_components / dash_html_components.
- Start the app with app.run(debug=True)  (run_server is gone).
- Get the data with `from data import bonds, history`.
- Give every component a callback uses an explicit id.
- No global state in callbacks; use dcc.Store.
- After a change, list each Input(id.prop) -> Output(id.prop).
Why it matters
  • Models have seen years of old Dash code: dash_core_components, app.run_server, @app.callback
  • Naming the data and its columns stops invented files
  • "List the Input → Output pairs" lets you check the wiring before reading the code
23:00–24:15. The single most useful trick for code generation: a short instructions file with versions, data, and conventions.

Taking it further

Deploy
  • server = app.server → gunicorn app:server
  • several workers ⇒ no globals; share state via dcc.Store, a cache or a DB
  • cache slow loads (flask-caching)
Grow
  • multi-page apps: use_pages=True + pages/
  • big data on charts: Patch, plotly-resampler
